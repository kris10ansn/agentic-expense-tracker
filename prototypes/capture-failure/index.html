Design assumptions & implementation notes For discussion

Keep outcome and resolution separate. A completed capture can still have unresolved items. Saving or ignoring one of those items does not change the original capture outcome.

Only say “nothing saved” when it is known. The current backend can mark a capture failed after expense insertion. The unknown-outcome example asks the user to check saved expenses before retrying.

Recovery is proposed behavior. Retry, dismiss, ignore, and correction are simulated here. Production needs durable capture history and resolution state. The current capture list only returns active jobs, and a completed capture disappears from Home.

Use the data already available. Item failures include source text, a reason, partial expense fields, and suggested values. Original image previews and automatic retry after reload need retained source files. Detailed capture-level errors also need to be persisted if they should survive reload.

A saved expense is the only thing that affects totals. Reviewing, hiding, or retrying a capture must not add its unsaved items to expense totals. A retry must reconcile existing expenses before writing again.
